# Spec: Bug record -- v1

> Normative specification. **Status: DRAFT (unstable -- will change).** This
> document uses [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) keywords:
> MUST, SHOULD, MAY.

## Motivation

The bug track (ADR-0020) carries a bug from a public issue to a draft pull request through
several stages, run by different leaves, possibly from different vendors, on different
machines (ADR-0021). The bug record is what passes between them. It has to be written down
for three reasons:

- **It is the trust boundary.** Every stage after Summarize reads the record instead of the
  issue. Whatever the record lets through reaches a leaf that runs `Bash` on the target
  project, so what it may contain must be a rule a program checks, not a prompt.
- **It separates what a model says from what the driver decides.** Leaves describe the bug
  and write the test; the driver records results, the target ref and routing. That split
  holds only if it is part of the format.
- **It outlives a run.** A track can stay open across an instance's `copier update`, so a
  record written by one release of the driver must be read correctly, or refused, by the
  next.

## Scope

This specification defines the bug record document: its encoding, its fields, which stage
writes each section, the validation a reader performs, how a leaf hands its part over, and
how the driver detects a record it did not write.

It does not define:

- the directory a record is kept in, which ADR-0020 section 8 decides, or how it relates
  to the bundle format (`bundle-format/v1`, planned in #712);
- the issue form a reporter fills in; section "Intake" below says only what Summarize may
  take from it;
- the stage logic, triggers, target-ref choice and protected paths, which ADR-0020 decides.
  This spec gives them fields, not rules.

## Conventions

- A **record** is one JSON document per bug, encoded as UTF-8 and conforming to I-JSON
  (RFC 7493): no duplicate member names, no unpaired surrogates, numbers within IEEE 754
  double precision.
- A **writer** produces or changes a record; a **reader** parses and validates one. The
  driver is both. A leaf is never a reader of sections it did not write and produces only
  the fragment its stage owns (see "Ownership").
- **Text fields** are strings meant for people. **Identifier fields** are strings matched
  against a fixed pattern.
- A **ref** is a Git branch name, written without `refs/heads/` (for example `main`,
  `release/0.1`). A **commit** is a full 40-character lowercase hexadecimal object ID.
- "Absent" means the member is not present. `null` is allowed only where this spec says so.

## Requirements

### 1. Top level

A record MUST be a JSON object with exactly these members:

| Member | Type | Written by | Meaning |
|---|---|---|---|
| `format` | string, exactly `"pdca.bug-record"` | driver | Identifies the document type |
| `version` | integer, exactly `1` | driver | This specification's version |
| `source` | object (§2) | driver | Where the bug came from |
| `summary` | object (§3) | Summarize leaf, validated by the driver | The sanitized description |
| `reproduction` | object (§4) or `null` | Reproduce leaf (`test`) and driver (the rest) | The red test and its results |
| `target` | object (§5) or `null` | driver | Where the fix goes |
| `routing` | object (§6) or `null` | driver | Whether a cycle may start without a maintainer |

A reader MUST reject a record with a member missing, a member not listed here, or a member
of the wrong type. This holds at every level of the document: v1 has no extension members.

`reproduction`, `target` and `routing` are `null` until their stage has run. A record in
which `target` is not `null` MUST have a non-null `reproduction` whose `status` is
`"reproduced"`; one in which `routing` is not `null` MUST have a non-null `target`.

### 2. `source`

| Member | Type | Meaning |
|---|---|---|
| `kind` | `"issue"` or `"scheduled-run"` | An issue in the tracker, or a failing test from the instance's own scheduled runs (ADR-0020, stage 4) |
| `repository` | string, `owner/name` | The repository the bug is filed against |
| `issue` | integer ≥ 1, or `null` | The issue number; MUST be non-null when `kind` is `"issue"` and `null` otherwise |
| `run` | string of 1–128 characters from `[A-Za-z0-9._-]`, or `null` | The scheduled run's ID; MUST be non-null when `kind` is `"scheduled-run"` and `null` otherwise |

### 3. `summary`

The summary is the only part of the record derived from text a stranger wrote.

| Member | Type | Limit | Meaning |
|---|---|---|---|
| `title` | text | 1–120 characters | One line naming the defect |
| `description` | text | 1–600 characters | What goes wrong, in plain language for someone who does not know the code |
| `impact` | text | 1–600 characters | Who is affected and what it costs them (lost data, a wrong result, a crash, a slowdown) |
| `observed` | text | 1–1500 characters | What happens |
| `expected` | text | 1–1500 characters | What should happen instead |
| `trigger` | text | 1–1500 characters | The conditions under which it happens |
| `areas` | array of 1–2 identifier strings | from the instance's area labels | Where the defect lives; the same values as ADR-0017's `area:*` labels, without the prefix |
| `reported_ref` | object | | The version the reporter saw the bug on (below) |
| `truncated` | boolean | | `true` if the leaf had to shorten the issue text it was given |

`reported_ref` has two members:

- `kind`: `"ref"`, `"tag"`, `"commit"` or `"none"`.
- `value`: a ref, a tag name, or a commit, matching `kind`; `null` when `kind` is `"none"`.

**Sanitization.** The driver MUST validate every text field of `summary` before it writes
the record, and MUST reject the leaf's output, never repair it, when a text field:

- contains a run of five or more consecutive words that also appears in the issue's title
  or body (comparison case-insensitive, on words separated by whitespace and punctuation);
- contains a number of three or more digits that also appears in the issue;
- contains a token of eight or more characters that contains a digit or one of
  `. / _ : = @ +`, or two or more hyphens (a likely identifier, path, host name, token or
  repository name);
- contains a URL, a Markdown link or image, a code span or fence, an HTML tag, or an
  `@`-mention;
- contains a control character other than a line feed.

These are the reason-field rules of ADR-0017 section 5 applied to the whole summary. They
make the summary say *what kind of thing* fails, never *which literal input* makes it fail;
the Reproduce leaf rediscovers the literals from the code. When the leaf's output is
rejected, the driver MAY ask the leaf once more and otherwise stops the track for the issue
with `needs-triage`.

**`reported_ref`.** The driver MUST check that a `reported_ref` other than `"none"` names a
ref, tag or commit that exists in `source.repository`, and MUST replace it with
`{"kind": "none", "value": null}` when it does not. A leaf's guess never becomes a ref the
driver checks out.

### 4. `reproduction`

| Member | Type | Written by | Meaning |
|---|---|---|---|
| `status` | `"reproduced"` or `"not-reproduced"` | driver | Whether a red test was found within the stage's budget |
| `test` | object (below), or `null` | Reproduce leaf, validated by the driver | The red test; MUST be non-null exactly when `status` is `"reproduced"` |
| `results` | array of result objects (below) | driver | The test run on each candidate ref; at least one when `status` is `"reproduced"` |
| `questions` | array of 0–5 text strings, each 1–300 characters | Reproduce leaf, validated by the driver | What the reporter would have to tell; MUST be empty when `status` is `"reproduced"` |

`questions` are posted to the public issue. The driver MUST apply the sanitization rules of
§3 to them.

`test`:

| Member | Type | Meaning |
|---|---|---|
| `kind` | `"unit"`, `"property"` or `"simulation-seed"` | What kind of test it is |
| `path` | string | The test file, relative to the repository root, using `/`; MUST NOT be absolute, contain `..`, or point inside `.git/` |
| `sha256` | 64 lowercase hexadecimal characters | The SHA-256 of the test file's bytes when Reproduce finished |
| `seed` | string of 1–64 characters from `[A-Za-z0-9_-]`, or `null` | The seed; MUST be non-null exactly when `kind` is `"simulation-seed"` |
| `command` | array of 1–32 strings, each 1–256 characters | The argument vector that runs the test, executed without a shell |

The driver MUST compute `sha256` itself from the file the leaf left, not take the leaf's
value. The gate of every cycle the record starts MUST refuse a sign-off when the test file's
SHA-256 differs from `sha256` (ADR-0020, stage 4).

A result object:

| Member | Type | Meaning |
|---|---|---|
| `ref` | ref | The candidate ref the test ran on |
| `commit` | commit | The commit `ref` pointed to at the time |
| `outcome` | `"red"`, `"green"` or `"error"` | Fails as expected, passes, or could not run (build failure, infrastructure) |

An `"error"` outcome is not evidence either way. Results are listed in the order they were
run; a ref MUST NOT appear twice.

### 5. `target`

| Member | Type | Meaning |
|---|---|---|
| `decision` | `"fix-on-main"`, `"backport-existing"`, `"fix-on-integration-line"` or `"answer-only"` | The four outcomes of ADR-0020 section 4 |
| `ref` | ref, or `null` | Where the fix is built or backported first; `null` only for `"answer-only"` |
| `backports` | array of refs | Further release branches that get a backport cycle; empty unless `decision` is `"fix-on-main"` or `"backport-existing"` |
| `fixing_commit` | commit, or `null` | The commit on `main` found by bisection; MUST be non-null exactly when `decision` is `"backport-existing"` |
| `answered_release` | string of 1–64 characters, or `null` | The first release in which the test is green; MUST be non-null exactly when `decision` is `"answer-only"` |

Every ref in `ref` and `backports` MUST appear in `reproduction.results` with outcome
`"red"`.

### 6. `routing`

| Member | Type | Meaning |
|---|---|---|
| `protected` | boolean | Whether any matched path is in the instance's protected paths |
| `matched` | array of strings | The protected-path patterns that matched; empty exactly when `protected` is `false` |
| `start` | `"auto"` or `"maintainer"` | Whether the cycle starts on its own or waits for the milestone (ADR-0020 section 3) |

`start` MUST be `"maintainer"` when `protected` is `true`. Routing is recomputed when a
cycle's diff is known; it may move from `"auto"` to `"maintainer"`, never back.

### 7. Ownership

The record mirrors ADR-0017's rule that the model classifies and the code decides:

- A leaf's output for its stage MUST be a JSON object holding only the members that stage
  writes: `summary` for Summarize; `test` and `questions` for Reproduce. The driver MUST
  reject leaf output with any other member, before validating content.
- `source`, `reproduction.status`, `reproduction.results`, `target` and `routing` are
  written only by the driver, from facts it established itself.
- Once `reproduction.status` is `"reproduced"`, a writer MUST NOT change `summary` or
  `reproduction.test`. A changed bug is a new record.

### 8. Intake

The issue form of an instance's repository SHOULD ask for the version or commit the
reporter used. Summarize MAY derive `summary.reported_ref` from that answer, subject to the
check in §3. Nothing else from the form has a field of its own; it reaches the record only
through the sanitized text fields.

### 9. Leaf output

A leaf hands over its part as one file with a fixed name in its output directory:
`summarize.out.json` for Summarize, `reproduce.out.json` for Reproduce. The file MUST be a
single JSON document as in "Conventions" and MUST hold only the members of §7.

The driver MUST read that file and nothing else. It MUST NOT extract JSON from a leaf's
standard output, from a transcript, or from prose around a code block. A missing file, an
empty file or a file that does not parse means the stage failed; it is never read as an
empty result.

### 10. One record per file, Markdown only rendered

A record is stored as its own file, `bug-record.json`, holding exactly one record. It is
never embedded in another document and records are never concatenated.

Any Markdown about a bug (the bundle's `README.md`, the cycle's brief, comments on the
issue) is rendered from the record by the driver. A writer MUST NOT read state back from
such Markdown; the record is the only source. This keeps the bug track out of the problem
risk R5 describes, where state lives in model-written Markdown that every reader parses.

### 11. Integrity

Every stored record is accompanied by a MAC file, `bug-record.json.mac`, next to it.

- The MAC file holds exactly one line: `hmac-sha256 <key-id> <mac>`, fields separated by
  one space, ended by one line feed. `<key-id>` is 1–64 characters from
  `[A-Za-z0-9._-]`; `<mac>` is 64 lowercase hexadecimal characters.
- `<mac>` is HMAC-SHA256 (RFC 2104) over the exact bytes of `bug-record.json`. There is
  no canonical form: changing any byte, including whitespace, changes the MAC.
- The key is a secret of at least 32 random bytes, held only on the workflow host and
  identified by `<key-id>` so it can be rotated. It MUST NOT reach a runner, a leaf, a
  repository or a log.
- The driver MUST write the record and then its MAC on every change, and MUST verify the
  MAC before using a record. A missing MAC file, an unknown key ID or a mismatch stops the
  track with a NEEDS-HUMAN item. The driver MUST NOT repair or re-MAC a record that failed
  verification.
- Leaf output (§9) carries no MAC: leaves hold no key. The driver validates it, merges it
  into the record and writes a new MAC.

A MAC, not a signature: the driver both writes and reads records, so a shared secret
suffices, and HMAC is in the standard library the driver is limited to (ADR-0008).

### 12. Publication

A record and its MAC file may be committed to a public repository (ADR-0020 section 8).
Writers MUST therefore put nothing in a record that is not fit to publish. The rules of §3
keep issue text out; in addition, no member may hold a secret, a signed URL, a host name
or path of the workflow host, or an identifier of the runner's infrastructure. A
published MAC reveals nothing about the key.

## Versioning and compatibility

- A reader MUST reject a record whose `format` is not `"pdca.bug-record"` or whose
  `version` it does not implement. It MUST NOT guess.
- Any change to a member, a type, a limit, a sanitization rule or an ownership rule is a
  new version. v1 has no compatible extensions.
- A driver that implements a later version SHOULD keep reading v1 records until no open
  track holds one, so a track started before a `copier update` can finish. A driver that
  cannot read a record MUST stop that track with a NEEDS-HUMAN item rather than restart
  it.

## Conformance

A conforming reader MUST accept every record under `vectors/v1/valid/` and reject every
record under `vectors/v1/invalid/`, for the reason given in the matching `.reason.txt`.

The sanitization rules of §3 compare a summary against the issue it came from, so their
vectors live apart, under `vectors/v1/sanitization/`. Each record there is structurally
valid and comes with the issue text as `<name>.issue.txt`. A conforming summary validator
MUST accept every record under `sanitization/accept/` and reject every record under
`sanitization/reject/`, for the reason in its `.reason.txt`.

Integrity vectors live under `vectors/v1/integrity/`. `test-key.txt` holds a key for
tests only, as hexadecimal, with key ID `test-1`. A conforming driver MUST accept the
record under `accept/` with its MAC file and MUST refuse every record under `reject/`,
for the reason in its `.reason.txt`.

Vectors are part of this version: changing, adding or removing one after v1 is stable is a
spec change (ADR-0018).

- **[OPEN]** Whether the thresholds of §3 (five words, three digits, eight characters) are
